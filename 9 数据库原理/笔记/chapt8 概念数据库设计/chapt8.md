## 8.1 ER 图转关系模式解题算法

ER 图转关系模式是从概念设计进入逻辑设计的关键步骤。做题时可以按固定算法处理，不要一边想一边乱建表。

### 8.1.1 总体解题顺序

```text
先处理实体
  -> 再处理弱实体
  -> 再处理 1:1 联系
  -> 再处理 1:N 联系
  -> 再处理 M:N 联系
  -> 再处理多值属性
  -> 最后统一检查主码、外码和联系属性
```

答题格式通常写成：

```text
关系名(主码, 普通属性, 外码)
主码：...
外码：... 参照 ...
```

如果题目要求写 SQL，再把关系模式翻译成 `CREATE TABLE`。

---

### 8.1.2 强实体型转换规则

**规则：每个强实体型转换为一个关系模式。**

转换方法：

- 实体名 -> 表名。
- 简单属性 -> 字段。
- 主属性 -> 主码。
- 复合属性 -> 拆成其组成的简单属性。
- 派生属性 -> 通常不存储，除非题目明确要求保存。

模板：

```text
实体E(主码, 属性1, 属性2, ...)
```

例子：

```text
Artist(ArtistID, Name, Specialty, Masterpiece)
Artwork(ArtworkID, Title, CreationTime, Category, Description)
Customer(CustomerID, Name, Phone, Address)
Location(LocationID, LocationName)

Artist 主码：ArtistID
Artwork 主码：ArtworkID
Customer 主码：CustomerID
Location 主码：LocationID
```

这是实验七美术馆题干中的四个主要实体。`CreationTime`、`Category`、`Description` 是艺术品的普通属性；如果题目只说“场所名称”，也可以补一个 `LocationID` 作为编号属性，便于建主码。

---

### 8.1.3 弱实体转换规则

**规则：弱实体转换为一个关系模式，并把所依赖强实体的主码加入弱实体关系中。**

转换方法：

- 弱实体自身属性放入关系。
- 父实体主码作为外码加入。
- 弱实体的主码通常由“父实体主码 + 弱实体部分键”组成。

模板：

```text
弱实体W(父实体主码, 部分键, 其他属性)
主码：(父实体主码, 部分键)
外码：父实体主码 参照 父实体
```

例子：

```text
ArtworkImage(ArtworkID, ImageNo, ImageURL, Caption)
主码：(ArtworkID, ImageNo)
外码：ArtworkID 参照 Artwork(ArtworkID)
```

实验七原题没有弱实体。这里补充同一美术馆场景：如果每件艺术品可以附多张图片，图片编号 `ImageNo` 只在某一件艺术品内部有意义，不能脱离 `Artwork` 独立存在，那么“艺术品图片”可看作依赖于“艺术品”的弱实体。

---

### 8.1.4 1:1 联系转换规则

**规则：1:1 联系通常把任意一方的主码放入另一方作为外码。**

优先选择：

1. 如果一方是全部参与，把另一方主码放到全部参与的一方。
2. 如果双方都是全部参与，可以考虑合并两个实体。
3. 如果联系有属性，把联系属性放到接收外码的那一方。

模板：

```text
A(A_ID, ...)
B(B_ID, ..., A_ID, 联系属性)
外码：A_ID 参照 A(A_ID)
```

**注意：如果题目没有特别说明，一般不单独对1:1的联系建联系表，除非为了表达清楚或有特殊约束。**

例子：

```text
Location(LocationID, LocationName)
GalleryRoom(RoomID, RoomName, LocationID, OpenDate)
主码：GalleryRoom.RoomID
外码：GalleryRoom.LocationID 参照 Location(LocationID)
```

实验七原题没有明确 1:1 联系。这里补充同一美术馆场景：如果每个展出场所只对应一个主展厅，每个主展厅也只属于一个展出场所，那么可以把 `LocationID` 放入 `GalleryRoom`，并把联系属性 `OpenDate` 一并放入接收外码的一方。实际 SQL 中若要严格表达 1:1，还应给 `LocationID` 加唯一约束。

---

### 8.1.5 1:N 联系转换规则

**规则：把 1 端实体的主码加入 N 端实体关系中，作为外码。**

转换方法：

- 1 端主码 -> N 端外码。
- 联系本身的属性 -> 通常也放到 N 端。

模板：

```text
A(A_ID, ...)
B(B_ID, ..., A_ID, 联系属性)
外码：A_ID 参照 A(A_ID)
```

例子：

实验七的“创作”联系：一位艺术家可以创作多件艺术品，一件艺术品只有一位创作者。

```text
Artist(ArtistID, Name, Specialty)
Artwork(ArtworkID, Title, CreationTime, Category, ArtistID)
主码：ArtworkID
外码：ArtistID 参照 Artist(ArtistID)
```

艺术家是 1 端，艺术品是 N 端，所以 `ArtistID` 放进 `Artwork`。

实验七的“购买”联系也是 1:N：一个顾客可以购买多件艺术品，一件实物艺术品最多卖给一个顾客，联系属性 `BuyTime`、`Price` 放到 N 端 `Artwork`。

```text
Customer(CustomerID, Name, Phone, Address)
Artwork(ArtworkID, Title, CreationTime, Category, ArtistID, CustomerID, BuyTime, Price)
Artwork 外码：CustomerID 参照 Customer(CustomerID)
```

---

### 8.1.6 M:N 联系转换规则

**规则：M:N 联系单独建一张中间表。**

记法：把两边实体的主码放进中间表，通常作为联合主码，同时也是外码。若联系本身有属性，也放进这张中间表。

模板：

```text
R(A_ID, B_ID, 联系属性...)
主码：(A_ID, B_ID)
外码：A_ID 参照 A(A_ID)
外码：B_ID 参照 B(B_ID)
```

例子：

实验七的“关注/感兴趣”联系是 M:N：一个顾客可关注多位艺术家，一位艺术家可被多个顾客关注。

```text
Interest(CustomerID, ArtistID)
主码：(CustomerID, ArtistID)
外码：CustomerID 参照 Customer(CustomerID)
外码：ArtistID 参照 Artist(ArtistID)
```

写成 SQL 就是：

```sql
CREATE TABLE Interest (
    CustomerID INT NOT NULL,
    ArtistID INT NOT NULL,
    PRIMARY KEY (CustomerID, ArtistID),
    FOREIGN KEY (CustomerID) REFERENCES Customer(CustomerID),
    FOREIGN KEY (ArtistID) REFERENCES Artist(ArtistID)
);
```



---

### 8.1.7 多值属性转换规则

**规则：多值属性必须单独转换为一个关系模式。**

转换方法：

- 原实体主码加入新关系。
- 多值属性作为新关系的属性。
- 新关系主码通常为“原实体主码 + 多值属性”。

模板：

```text
E(E_ID, ...)
E_MultiValue(E_ID, MultiValueAttr)
主码：(E_ID, MultiValueAttr)
外码：E_ID 参照 E(E_ID)
```

例子：

实验七原题把顾客电话作为普通属性。若题目进一步说明“一个顾客可以有多个联系方式”，则 `Phone` 是多值属性，应单独拆表：

```text
Customer(CustomerID, Name)
CustomerPhone(CustomerID, Phone)
主码：(CustomerID, Phone)
外码：CustomerID 参照 Customer(CustomerID)
```

---

### 8.1.8 三元联系转换规则

**规则：三元联系通常转换为一个独立关系模式。**

转换方法：

- 三个参与实体的主码全部加入新关系。
- 三个主码通常共同组成主码。
- 联系自身属性加入该关系。
- 三个主码都是外码。

模板：

```text
R(A_ID, B_ID, C_ID, 联系属性)
主码：(A_ID, B_ID, C_ID)
外码：A_ID 参照 A(A_ID)
外码：B_ID 参照 B(B_ID)
外码：C_ID 参照 C(C_ID)
```

注意：三元联系一般不能简单拆成三个二元联系，否则可能丢失语义。

例子：

实验七原题没有三元联系。这里补充同一美术馆场景：如果要记录“某顾客在某个展出场所预约观看某件艺术品”，这个事实同时依赖顾客、艺术品、场所三方。

```text
VisitAppointment(CustomerID, ArtworkID, LocationID, AppointmentTime)
主码：(CustomerID, ArtworkID, LocationID, AppointmentTime)
外码：CustomerID 参照 Customer(CustomerID)
外码：ArtworkID 参照 Artwork(ArtworkID)
外码：LocationID 参照 Location(LocationID)
```

不能简单拆成“顾客-艺术品”“顾客-场所”“艺术品-场所”三个二元联系，因为拆开后无法表达“这个顾客在这个场所预约观看这件艺术品”这个完整事实。

### 8.1.9 超类/子类转换规则

超类/子类有多种转换方法，考试或作业中常用以下写法。

#### 方法一：超类一张表，子类各一张表

适合子类有自己特殊属性的情况。

```text
Superclass(SuperID, 公共属性)
Subclass1(SuperID, 子类1特殊属性)
Subclass2(SuperID, 子类2特殊属性)
```

子类表的 `SuperID` 既是主码，也是外码。

例子：

```text
Artwork(ArtworkID, Title, Year, Price)
Painting(ArtworkID, Technique)
Sculpture(ArtworkID, Material)
```

在美术馆场景中，`Artwork` 是超类，`Painting`、`Sculpture` 是子类。`Painting.ArtworkID` 和 `Sculpture.ArtworkID` 既是各自表的主码，也是参照 `Artwork(ArtworkID)` 的外码。

#### 方法二：只建子类表

适合每个超类实例都必须属于某个子类，且子类之间不重叠。

```text
Painting(ArtworkID, Title, Year, Price, Technique)
Sculpture(ArtworkID, Title, Year, Price, Material)
```

#### 方法三：只建一张总表

适合子类差异较少的情况。

```text
Artwork(ArtworkID, Title, Year, Price, Type, Technique, Material)
```

缺点：可能出现较多 NULL。

### 8.2.1 数据库系统开发生命周期

数据库系统开发不是直接写 SQL，而是一个完整生命周期：

1. **数据库规划**：确定建设数据库系统的目标、范围和资源。
2. **系统定义**：明确系统边界、用户视图和应用范围。
3. **需求采集与分析**：收集用户的数据需求、业务规则和事务需求。
4. **数据库设计**：进行概念设计、逻辑设计和物理设计。
5. **实现**：在具体 DBMS 中创建数据库对象。
6. **数据转换与装载**：把旧系统或外部数据转换并导入新数据库。
7. **测试**：检查数据库结构、约束、事务、性能是否满足需求。
8. **运维管理**：维护数据库运行、安全、备份、恢复和性能优化。

核心理解：数据库设计只是生命周期中的一个阶段，但它决定了后续实现、测试和维护的基础质量。

---

### 8.2.2 数据库设计方法论

#### 8.2.2.1 设计方法论的定义

**数据库设计方法论 (database design methodology)** 是一种结构化方法，使用过程、技术、工具和文档来支持并促进数据库设计过程。

如果数据库较复杂，就需要系统化方法来保证：

- 满足用户需求。
- 符合业务规则。
- 达到预期性能要求。
- 便于后续实现、维护和扩展。

#### 8.2.2.2 方法论的输出文档

概念数据库设计阶段通常产生：

- **ER 图 (Entity-Relationship Diagram)**：表示实体、属性、联系和约束。
- **数据字典 (Data Dictionary)**：记录实体、属性、联系、域、码等详细说明。

ER 图负责“看懂结构”，数据字典负责“说清细节”。

---

### 8.2.3 数据库设计的三个阶段

数据库设计主要分为三个阶段：概念设计、逻辑设计、物理设计。

#### 8.2.3.1 概念数据库设计

**Conceptual database design** 是构造企业所使用信息模型的过程，独立于所有物理考虑。

特点：

- 面向现实世界和用户需求。
- 不依赖具体 DBMS。
- 不考虑表如何存储、索引如何建立等物理细节。
- 主要产物是概念数据模型，如 ER 图。

#### 8.2.3.2 逻辑数据库设计

**Logical database design** 是基于特定数据模型构造组织数据模型的过程，但仍独立于具体 DBMS 和物理存储。

特点：

- 把概念模型转化为逻辑模型。
- 在关系数据库中，通常表现为把 ER 图转换为关系模式。
- 需要确定表、字段、主码、外码和完整性约束。
- 不具体讨论文件组织、索引实现等物理细节。

#### 8.2.3.3 物理数据库设计

**Physical database design** 是描述数据库在辅助存储器上如何实现的过程。

内容包括：

- 基表设计。
- 文件组织方式。
- 索引设计。
- 完整性约束。
- 安全限制。
- 为高效访问数据而进行的存储和性能设计。

三阶段关系可以概括为：

```text
现实业务需求
    -> 概念设计：ER 图
    -> 逻辑设计：关系模式
    -> 物理设计：表、索引、存储、约束、安全
```

---

### 8.2.4 数据库设计成功因素

数据库设计的关键成功因素包括：

1. **尽可能与用户交互**：用户最了解真实业务规则。
2. **遵循结构化方法**：设计过程不能凭感觉随意画图。
3. **采用数据驱动方法**：先关注数据本身，而不是先写程序。
4. **考虑结构和完整性要求**：模型中要体现约束、主码、外码、参与约束等。
5. **使用概念化、规范化和事务验证技术**：保证模型合理且能支持业务操作。
6. **尽可能用图表示数据模型**：ER 图比纯文字更适合表达结构。
7. **使用数据库设计语言 DBDL**：用规范语言描述模型。
8. **建立数据字典**：补充 ER 图无法完整表达的细节。
9. **愿意反复迭代**：数据库设计常常需要修改、验证、再修改。

---

### 8.2.5 概念数据库设计方法总览

概念数据库设计的核心任务是：**为企业的每个用户视图建立局部概念数据模型，然后合并成全局概念数据模型**。

#### 8.2.5.1 局部视图与全局视图

- **局部概念数据模型 (local conceptual data model)**：针对某一个用户视图建立的 ER 模型。
- **全局概念数据模型 (global conceptual data model)**：将多个局部模型合并后得到的整体模型。

例如学生信息系统中，不同部门看到的学生信息不同：

- 教师视图：学号、姓名、性别、系别、学历等。
- 教务视图：学号、姓名、出生年月、学籍信息等。
- 学生处视图：家庭出身、籍贯、政治面貌、奖惩记录、家庭成员等。

这些视图需要先分别建模，再整合成统一的学生概念模型。

---

### 8.2.6 Step 1 建立局部概念数据模型

课件中 Step 1 是概念数据库设计的核心，共包含 9 个子步骤。

#### 8.2.6.1 Step 1.1 识别实体型

目标：识别用户视图中的主要实体。

方法：

- 检查需求说明中的**名词或名词短语**。
- 重点关注人、地点、物、组织、事件、概念等主要对象。
- 排除那些只是其他对象性质的名词。

实体型识别后，要在数据字典中记录实体名称和描述。

#### 实体与属性的区分准则

判断一个事物是实体还是属性时，可以看：

1. **属性不能再具有需要描述的性质**：属性应该是不可再分的数据项。
2. **属性不能与其他实体发生联系**：联系只发生在实体之间。

原则：凡是能作为属性处理的，通常尽量作为属性，以简化 ER 图。

例子：

- “职称”通常可以作为教师的属性。
- 但如果系统中“住房分配”与“职称”有关，职称需要和住房发生联系，此时“职称”更适合作为实体。

#### 8.2.6.2 Step 1.2 识别联系型

目标：识别实体之间的业务联系。

方法：

- 检查需求说明中的**动词或动词短语**。
- 分析实体之间发生了什么业务行为。
- 判断联系的类型和参与基数。

需要确定：

- 联系是一元、二元还是多元。
- 联系是 1:1、1:N 还是 M:N。
- 实体参与联系是全部参与还是部分参与。
- 联系是否具有自身属性。

定义联系时要注意：

1. **消除冗余联系**：如果某联系可由其他联系推出，一般不需要保留。
2. **正确区分二元联系和多元联系**：多元联系通常不能简单拆成多个二元联系。
3. **防止语义缺陷**：避免模型表达不清或造成查询歧义。

#### 8.2.6.3 Step 1.3 识别并关联属性

目标：识别实体或联系的属性，并把属性关联到正确对象上。

属性通常来自需求中的名词或名词短语，当它们表示：

- 性质，如颜色、重量。
- 标识符，如编号、ID。
- 特征值，如年龄、价格。

属性文档化时应记录：

- 属性名称和描述。
- 数据类型和长度。
- 别名。
- 是否必须指定，即是否允许 NULL。
- 是否为多值属性。
- 是否为复合属性，如果是，要说明由哪些简单属性组成。
- 是否为派生属性，如果是，要说明计算方式。
- 默认值。

#### 8.2.6.4 Step 1.4 确定属性域

**属性域 (domain)** 是属性可取值的集合。

属性域需要说明：

- 允许取值范围。
- 数据格式。
- 数据长度。

例子：

- 性别域：`{男, 女, 其他}`。
- 日期域：格式为 `YYYY-MM-DD`。
- 姓名域：`VARCHAR(50)`。

确定属性域可以减少非法数据，保证数据完整性。

#### 8.2.6.5 Step 1.5 确定候选码、主码和备用码

#### 候选码

**候选码 (candidate key)** 是能够唯一标识实体实例的最小属性集。

特点：

- 候选码不能为 NULL。
- 一个实体可以有多个候选码。

#### 主码

**主码 (primary key)** 是从候选码中选出的主要标识符。

#### 备用码

没有被选为主码的候选码称为 **备用码 (alternate key)**。

#### 主码选择原则

选择主码时，优先选择：

1. 属性数最少的候选码。
2. 值最不容易变化的候选码。
3. 未来最不容易失去唯一性的候选码。
4. 字符型属性中长度较短的候选码。
5. 数值型属性中最大值范围较小的候选码。
6. 从用户角度最容易使用的候选码。

#### 8.2.6.6 Step 1.6 考虑增强建模概念

这是可选步骤，用于处理复杂业务结构。

常见增强建模概念：

- **Specialization / Generalization**：特殊化 / 泛化，即超类和子类。
- **Aggregation**：聚合，把联系视作更高层次对象参与其他联系。
- **Composition**：组合，表达整体与部分之间更强的依赖关系。

#### 超类与子类

- **超类 (superclass)**：更一般的实体类型。
- **子类 (subclass)**：更特殊的实体类型。

例子：

- 员工是超类。
- 全职员工、兼职员工是子类。

使用超类/子类可以更清楚表达业务层次，但也会增加模型复杂度。

#### 8.2.6.7 Step 1.7 检查模型冗余

目标：检查 ER 模型中是否存在冗余结构，并删除不必要的部分。

主要活动：

1. **重新检查 1:1 联系**：如果两个实体严格一一对应，可以考虑是否合并。
2. **删除冗余联系**：如果某联系能从其他联系推导出来，可考虑删除。
3. **考虑时间维度**：有些看似冗余的数据是为了保留历史快照，不能简单删除。

例子：

- 如果“客户”和“租约”已经通过 Holds 联系关联，又额外有可推导出的 Rents 联系，可能就是冗余。
- 但订单中的历史价格虽然可从商品当前价格查到，却不能删除，因为商品价格会随时间变化。

#### 8.2.6.8 Step 1.8 用用户事务验证模型

目标：检查 ER 模型是否支持用户需要执行的业务操作。

两种方法：

#### 描述法

对每个关键业务事务，列出它涉及的数据实体、属性和联系，再检查 ER 模型中是否存在对应结构。

例子：

事务：查询客户订单历史。

需要的数据：

- 客户实体。
- 订单实体。
- 产品实体。
- 客户与订单、订单与产品之间的联系。

#### 路径法

在 ER 图上标出业务事务的数据访问路径，检查路径是否完整。

步骤：

1. 确定事务起点实体。
2. 沿联系跟踪访问路径。
3. 验证路径能否覆盖业务所需数据。
4. 检查是否存在路径断裂、冗余路径或语义不清。

#### 8.2.6.9 Step 1.9 与用户复审模型

目标：与用户一起审核 ER 模型，确保模型真实反映组织的数据需求。

评审重点：

- 实体是否完整。
- 属性是否准确。
- 联系和基数约束是否符合业务规则。
- 是否支持用户实际事务。
- 是否存在争议业务规则。

评审成果：

- 修订后的 ER 图。
- 用户确认记录。
- 争议点记录。
- 需要进一步确认的问题。

### 8.2.7 合并局部模型为全局概念模型

当每个用户视图的局部概念模型建立完成后，需要把它们合并成全局概念模型。

合并时要处理：

- 同名实体是否表示同一概念。
- 不同名称是否其实表示同一实体。
- 属性是否重复或冲突。
- 联系是否重复、缺失或矛盾。
- 主码选择是否一致。
- 不同视图中的约束是否冲突。

全局模型应能统一表示所有用户视图的数据需求。

### 8.2.8 常见建模问题与检查

#### 8.2.8.1 Fan Trap 扇形陷阱

当一个实体通过多条路径与多个实体关联，导致查询路径不明确时，可能出现扇形陷阱。

本质问题：模型看起来有联系，但实际无法确定某个实体实例到底对应哪一个相关实例。

处理方法：

- 重新检查联系语义。
- 增加必要的直接联系。
- 拆分或重构联系路径。

#### 8.2.8.2 Chasm Trap 深坑陷阱

当两个实体之间的关联路径存在可选联系或部分参与，导致查询时丢失部分数据时，可能出现深坑陷阱。

本质问题：模型中存在路径，但不是所有实例都能沿该路径被访问到。

处理方法：

- 检查参与约束。
- 增加必要联系。
- 调整实体和联系的抽象方式。

#### 8.2.8.3 冗余联系

如果一个联系可以由其他联系推导得到，通常属于冗余联系。

但要注意：涉及历史记录、时间快照、审计追踪时，冗余可能是业务需要。

#### 8.2.8.4 参与约束

参与约束描述实体参与联系是否是强制的。

- **全部参与**：每个实体实例都必须参与该联系，ER 图中常用双线表示。
- **部分参与**：实体实例可以不参与该联系，ER 图中常用单线表示。

例子：

- 如果每个顾客必须至少购买过一件艺术品，顾客对购买联系是全部参与。
- 如果顾客可以只关注艺术家但未购买，则顾客对购买联系是部分参与。

## 本章速记

- 数据库设计分为：概念设计、逻辑设计、物理设计。
- 概念设计独立于 DBMS 和物理存储，核心产物是 ER 图和数据字典。
- 复杂数据库设计要采用结构化方法论。
- 概念设计先建立局部模型，再合并为全局模型。
- Step 1 的九个任务是本章核心。
- 实体看名词，联系看动词，属性看性质和标识符。
- 属性域用于限制属性取值。
- 候选码不可为空，主码从候选码中选择，剩余候选码是备用码。
- ER 模型要检查冗余、Fan Trap、Chasm Trap，并用用户事务验证。
- ER 图转关系模式口诀：实体变表，属性变字段，1:N 外码放 N 端，M:N 单独建表，多值属性单独建表。
- 最终模型必须和用户复审确认。
